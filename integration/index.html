    Integration Guide¶

    The library does not touch hardware. An integration has three parts:

    1. Receive: move bytes from the transport into dxl2_link_receive(). Do it in a thread or the main loop, not in an interrupt handler: the packet handler runs in the caller's context and usually sends a reply.
    2. Transmit: a dxl2_write_fn that writes a complete packet. Serialize it (mutex) if more than one thread can send.
    3. Application: a dxl2_packet_handler_t that interprets the instruction for its IDs (Control Table) and answers with dxl2_link_send_status().

    Complete, buildable programs for each pattern below are described in Examples.

    Zephyr: UART with an RX interrupt, byte queue and RX thread¶

    examples/zephyr is the structure used in the SmartManipulator-X firmware, reduced to the library API. The ISR only queues bytes; a thread owns the link. Select the UART with a dxl2,uart chosen node (see app.overlay.example) and build it with:

    west build -b <board> examples/zephyr -- -DDTC_OVERLAY_FILE=<board>.overlay

    Notes from the hardware bring-up:

    • Size the byte queue for at least one maximum packet plus the time the handler blocks (for example while it waits for a motor driver). A dropped byte makes the next packet fail its CRC; the parser recovers on the next header.
    • uart_poll_out() is simple and deterministic. At 230400 bit/s a 256-byte packet takes about 11 ms; use interrupt or DMA TX if that is too long.
    • Check the real bit rate of the UART divisor. A 16550-style UART at a 50 MHz clock gives 223214 bit/s for 230400 (-3.1 %), which is too far off; some UARTs (for example the SmartFusion2 MMUART) have a fractional divisor.
    • Text output (console, logs, printk) on the same UART corrupts the framing.

    Adding the library to a CMake build (Zephyr or any other)¶

    dxl2.cmake defines the dxl2 static library target with its include directories (. and inc/) and the version definitions:

    include(path/to/dxl2/dxl2.cmake)
target_link_libraries(app PRIVATE dxl2)

    In a Zephyr application also link the library to zephyr_interface, so it is compiled with the board's architecture flags (see examples/zephyr/CMakeLists.txt):

    target_link_libraries(dxl2 PUBLIC zephyr_interface)

    Without CMake, compile src/*.c and add the repository root and inc/ to the include path. Buffer sizes are set in inc/dxl2_config.h and can be overridden with compiler definitions (for example -DDXL2_MAX_PACKET_SIZE=1024U).

    Bare metal / other RTOS¶

    The same pattern applies (examples/bare_metal): ring buffer from the RX interrupt, drain it from the main loop into dxl2_link_receive(), and a blocking or buffered write function. On a host (Linux/Windows serial port, examples/host_serial) read whatever the port returns and pass it to dxl2_link_receive() in one call.

    Answering a device request¶

    A device implementation typically does this in the handler:

    static void on_packet(const struct dxl2_packet *packet, void *context)
{
    const uint8_t *p = packet->parameters;

    if (packet->id != MY_ID && packet->id != DXL2_BROADCAST_ID) {
        return;
    }
    switch (packet->instruction) {
    case DXL2_INST_PING:
        /* model number (2), firmware version (1) */
        break;
    case DXL2_INST_READ:
        if (packet->parameter_length != 4U) {
            dxl2_link_send_status(&link, MY_ID, DXL2_ERR_DATA_LENGTH, NULL, 0U);
            return;
        }
        /* address = dxl2_get_u16(&p[0]), length = dxl2_get_u16(&p[2]) */
        break;
    default:
        dxl2_link_send_status(&link, MY_ID, DXL2_ERR_INSTRUCTION, NULL, 0U);
        break;
    }
}

    Do not answer instructions sent to the broadcast ID, except PING (all devices answer, ordered by ID) and the read instructions that name the device in their ID list. Respect the device's Status Return Level and Return Delay Time registers if it emulates them.
